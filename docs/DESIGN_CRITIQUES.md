# NatForge — Design Critique Findings (from adversarial review)

## Reviewer (blocking=true)

The plan is largely sound architecturally and correctly preserves the working two-plane split, the yamux 0.13 poll-driver (mux.rs stays shape-compatible since OpenStream just gains a field the driver ignores), and the length-prefixed-then-yamux handshake. The peek-then-replay design is correct: HTTP/SNI bytes are consumed into `buf` on the core side and carried inside the NFS1 preamble's replay field, so `copy_bidirectional(&mut inbound, &mut outbound)` afterward does not double-send or lose them, and the agent reads the preamble via sequential read_exact on the .compat() stream before copy_bidirectional — no over-read. However there are several concrete compile-time and type-correctness bugs that will block a direct implementation, the most serious being a Postgres/sqlx type mismatch on route_id (u16 vs SMALLINT/i16), a missing redis `connection-manager` feature on website_backend, and an unresolved port_pool seeding ownership gap. These must be fixed before the plan compiles end-to-end.

- **[CRITICAL] website_backend/Cargo.toml + db layer (redis ConnectionManager)**
  - Problem: The plan's db/connection.rs uses `redis::aio::ConnectionManager` for the website, and crate_changes states website Cargo.toml 'already has sqlx/redis/dotenvy (verified) — add natforge-proto path dep'. But the real website Cargo.toml has `redis = { version = "0.27", features = ["tokio-comp"] }` — it does NOT enable `connection-manager`. I confirmed in redis-0.27.6/src/aio/mod.rs that `pub use connection_manager::*` is gated `#[cfg(feature = "connection-manager")]`, so `redis::aio::ConnectionManager` does not exist without that feature. The website code will not compile. The plan only adds the connection-manager feature to the CORE Cargo.toml (Step 4.1), never to the website.
  - Fix: Change website_backend/Cargo.toml to `redis = { version = "0.27", features = ["tokio-comp", "connection-manager"] }`. Apply the same to core_proxy_backend (Step 4.1 already does).
- **[CRITICAL] sql_schema routes.route_id + all RouteClaim/AgentRouteBinding/RouteResult structs**
  - Problem: Every Rust struct types `route_id` as `u16` (natforge-proto AgentRouteBinding, RouteResult, jwt RouteClaim, state.OpenStream.route_id, the preamble u16), but the schema declares `routes.route_id SMALLINT`. sqlx for Postgres has NO encode/decode impl for u16 — SMALLINT maps to i16 only. Any `query_as`/`query` binding or reading route_id as u16 (e.g. add_route, tunnels_for_owner JOIN, the FOR UPDATE SKIP LOCKED UPDATE that writes port_pool.route_id) will fail to compile (`the trait Type<Postgres> is not implemented for u16`). Same problem for `public_port INT` vs the `u16` used in RouteClaim.public_port / port_pool reads, and `local_port INT` vs `u16`.
  - Fix: Pick one of: (a) keep wire/proto types u16 but cast at the DB boundary (store as i32/i16, `value as i32` on write, `(row_i32 as u16)` on read) — document the cast helper in db/queries.rs; or (b) make the DB columns INT and read into i32 then convert. Be explicit that NO sqlx bind/read ever uses u16 directly. Also note SMALLINT is i16 (range to 32767) — fine for dense route ids, but the FOR-UPDATE port_pool query binds route_id, so cast there too.
- **[MAJOR] port_pool seeding ownership (sql_schema NOTE + Phase 1/Step 1.4)**
  - Problem: The plan makes the WEBSITE the 'allocator of record' for tcp ports via the Postgres port_pool table (FOR UPDATE SKIP LOCKED), but the port RANGE (PUBLIC_PORT_MIN/MAX) and node_id live in core_proxy_backend's config/env, not the website. The migration NOTE explicitly says port_pool is 'seeded at runtime per node on first boot (see redis_keys / startup), NOT here'. Yet request_tunnel runs in the website and must allocate from an already-seeded port_pool. Nothing in the plan actually seeds port_pool: the website doesn't know the range, and the core (which knows it) has no PgPool (decision #7 says 'Core does NOT get a PgPool'). Result: port_pool is empty, alloc_tcp_port returns no rows, every tcp route reservation fails.
  - Fix: Decide an owner. Cleanest: add a core->website internal endpoint `POST /api/internal/node_register { node_id, port_min, port_max, http_port, https_port, addr }` that the core calls on boot; the website upserts port_pool rows (INSERT ... ON CONFLICT DO NOTHING over generate_series(min,max)). Or give the website the range via its own env (PUBLIC_PORT_MIN/MAX/NODE_ID) and seed in AppState::connect after migrate. Specify which.
- **[MAJOR] core close_tunnel by tunnel_id vs subdomain-keyed map (Step 4.9 + state.rs)**
  - Problem: The plan changes the website->core stop call to `POST {core_url}/internal/tunnels/{tunnel_id}/stop` and says it 'aborts ActiveTunnel + all RouteHandles'. But CoreState.tunnels is `RwLock<HashMap<String, ActiveTunnel>>` keyed by subdomain (or "tid:<id>" for tcp-only). There is no index from tunnel_id -> map key, so the new handler can only find the tunnel by O(n) scanning every ActiveTunnel for `t.tunnel_id == id`. The plan never specifies this scan or a secondary tunnel_id->subdomain index, and the existing close_tunnel handler is keyed by subdomain. As written the route signature can't locate the tunnel.
  - Fix: Either add `pub tunnels_by_id: RwLock<HashMap<i64, String>>` (id -> map key) to CoreState updated on register/teardown, or have the website continue posting the subdomain (it owns the subdomain<->tunnel_id mapping in Postgres) and keep the subdomain-keyed core route. State the chosen key explicitly.
- **[MAJOR] tunnel teardown releases ports but website owns port_pool (Step 2.3 tunnel_down + handle_agent teardown)**
  - Problem: Decision #3 retires CoreState::release_port and makes the website the port authority. On agent disconnect, core's handle_agent teardown can no longer release the tcp port itself (no PgPool). It must rely on calling reporter::tunnel_down -> website tunnel_down to `UPDATE port_pool SET tunnel_id=NULL`. But reporter calls are 'best-effort' (failures only logged, never retried — see reporter.rs `post()`), so a dropped/failed tunnel_down silently leaks the pooled tcp port in Postgres until the deferred 'reconciliation sweep'. The plan mentions the sweep for crash recovery but not for ordinary best-effort POST loss, and never specifies the sweep's query/trigger concretely.
  - Fix: Specify the reconciliation sweep concretely (periodic website job: for tunnels whose `nf:tunnel:live:{subdomain}` Redis key is absent AND status!=awaiting_agent, release their port_pool rows + set status offline). Make tunnel_down idempotent. Optionally make the core's tunnel_down report retry a few times.
- **[MAJOR] TLS SNI parser 8192 cap vs real ClientHello size (wire_protocol SNI + shared.rs run_https)**
  - Problem: The SNI parser/buffer is capped at 8192 bytes and treats overflow as close. A TLS 1.3 ClientHello with many extensions, large key_share groups (e.g. post-quantum X25519MLKEM768 ~1216 bytes), GREASE, and ALPN can legitimately exceed 8192, and TLS records can be fragmented across multiple 5+rec_len records (the ClientHello handshake message can span multiple TLS records). The parser only buffers 'until 5+rec_len present' for a SINGLE record (`require b[0]==0x16 ... rec_len=u16(b[3..5])`), so a ClientHello fragmented across two records, or one exceeding the cap, fails closed and drops a valid client. Replay then also needs ALL those record bytes to be byte-exact for passthrough.
  - Fix: Raise the cap to at least 16384 (max TLS record) and, more importantly, handle multi-record ClientHello: keep reading records and concatenating handshake fragments until the handshake length (3-byte field after msg_type) is satisfied, OR document that v1 only supports single-record ClientHello (true for curl/openssl/most browsers) and fail-closed otherwise. The replay buffer must contain the exact raw bytes peeked (all records), which the design already does since replay = peeked buf.
- **[MINOR] HTTP keep-alive / multiple requests on one connection (shared.rs route_and_splice)**
  - Problem: route_and_splice peeks only the FIRST request's headers to pick the subdomain, then does raw copy_bidirectional for the rest of the connection. If the client reuses the TCP connection (HTTP/1.1 keep-alive) to send a SECOND request with a DIFFERENT Host (legal, and common with shared proxies/browsers coalescing), it is still routed to the first subdomain's agent. This is a known/acceptable L4-style limitation but the plan presents Host routing as general and does not call it out; it can cause silent cross-routing in test (4) if a client coalesces.
  - Fix: Document that routing is per-connection (first Host wins) and that connection coalescing across subdomains is out of scope, matching the SNI/L4 model. No code change required, but state it so the engineer/tests don't treat mis-coalesced requests as a bug.
- **[MINOR] Json<RequestTunnelReq> extractor vs current agent reserve() (Step 2.2 / Phase 3)**
  - Problem: request_tunnel becomes `Json(req): Json<RequestTunnelReq>`, which REQUIRES a non-empty body with Content-Type: application/json or axum 0.8 rejects with 415/422. The current agent reserve() in service_host.rs does `.post(...).bearer_auth(...).send()` with NO body. Until the agent is updated (Phase 3) the reserve call 4xxs. The plan ships these together so it's not a runtime regression, but the engineer must update reserve() to `.json(&RequestTunnelReq{routes})`; the plan's crate_changes mentions it but the wire_protocol/test_plan POSTs `-d '{...}'` via curl (which does NOT set application/json by default — curl -d sets application/x-www-form-urlencoded).
  - Fix: In the test_plan, curl must send `-H 'Content-Type: application/json' -d '{...}'` (or `--json`) or axum's Json extractor returns 415. Update all curl reservation calls accordingly, and ensure agent reserve() uses reqwest .json().
- **[MINOR] Single yamux driver serializes outbound opens across ALL routes (mux.rs unchanged + multi-route)**
  - Problem: One yamux session now multiplexes 1..N routes but still has ONE open_tx and ONE run_client_driver, whose state machine negotiates outbound opens strictly one at a time (`pending: Option<...>`, completes one poll_new_outbound before pulling the next from open_rx). With http+https+tcp all funneling inbound connections into the same open_tx, a burst of connections on a busy tcp route can head-of-line-block opens for the http route (and vice versa). This is the pre-existing behavior, not new, but multi-route makes contention materially worse and the plan's 'scale to MANY concurrent users' claim should acknowledge it.
  - Fix: No correctness bug — yamux opens are fast and this is acceptable for the thesis demo. Optionally note it as a known scaling characteristic; per-route open channels would still share one Connection, so the serialization is inherent to the single-driver model and fine to keep.
## Reviewer (blocking=true)

The plan is well-grounded in the real code (verified: yamux client/server split, single open_tx per session, stateless tunnel token, in-memory maps, existing stop_tunnel subdomain mismatch, redis 0.27 in lockfile, no migrations dir yet, docker-compose present, install.sh NoNewPrivileges=true with no User=). The architecture (preamble framing, subdomain-on-:80/:443 + dedicated tcp ports, website-as-port-allocator, two-plane split preserved) is sound and the chosen conflict resolutions are coherent. BLOCKING issues before implementation: (1) the idempotent re-reservation query is unspecified yet load-bearing — without it the 101-port pool leaks/exhausts on normal 10-min-token reconnects AND test step 6 cannot prove durability; (2) the redis 'connection-manager' feature is missing from website Cargo.toml and absent entirely from core, so it will not compile as described; (3) registration-side subdomain hijack (HashMap overwrite + ownership-blind teardown) needs a tunnel_id/generation guard. Major: serialized single-flight stream-open in mux.rs contradicts the 'unchanged + scales to many users' claim (pick: document the limit or pipeline the driver); teardown must reclaim BOTH route maps + Postgres port_pool via reconciliation, not just best-effort tunnel_down; DDoS blacklist is unbounded/no-TTL and source-IP-spoofable. Minor but real: SNI 8KiB cap will fail real browsers, frontend/API identifier drift (subdomain vs tunnel_id), non-atomic multi-route reservation should be one transaction, and the CAP_NET_BIND_SERVICE change is a no-op without a non-root User=. The SNI/Host inbound path is correctly anonymous (no spoofing risk there); the spoofing risk is at agent registration, not friend connection. Fix the three blockers and the four majors and this plan is implementable and locally provable.

- **[CRITICAL] Local-testability / yamux driver (mux.rs) — the core data-path will NOT carry multi-route traffic as written**
  - Problem: The plan keeps run_client_driver in core_proxy_backend/src/tunnel/mux.rs 'UNCHANGED in shape' and says OpenStream 'now carries route_id but driver just forwards reply'. But the driver is a single-flight state machine: it holds exactly ONE `pending: Option<oneshot::Sender>` and only pulls the next OpenStream from open_rx AFTER the previous poll_new_outbound completes (mux.rs lines 26, 44-66). With ONE shared open_tx per session feeding ALL routes (http+https+N tcp listeners all clone the same open_tx per the state.rs ActiveTunnel.open_tx / RouteHandle.open_tx design), concurrent inbound connections across routes serialize through one in-flight open. That is the EXISTING behavior and works for low concurrency, but the plan's scale claims (test step 4: 'unlimited-user sharing', many concurrent users) and step 5 (http + tcp 'over the SAME yamux session') run through this single-flight bottleneck. More importantly: poll_new_outbound() in yamux 0.13 returns a Stream with NO notion of which route it is — the route_id is only known to the CALLER (the listener that sent OpenStream). The plan's preamble write happens in bridge/route_and_splice AFTER the stream is handed back, so functionally correct, BUT the driver loop drops ALL inbound streams ('any inbound stream is simply dropped', line 33-34) and the plan never changes that — fine since agent=server. The real bug: nothing in the plan validates that one open_tx mpsc(128) shared by http+https+tcp listeners won't deadlock the driver when poll_new_outbound is Pending while open_rx has queued work. It won't deadlock, but throughput is 1 stream-open at a time across the whole tunnel. For a thesis demo this is acceptable; the plan must STOP claiming scale and explicitly document the single-flight open path, or widen the driver to pipeline opens.
  - Fix: Either (a) explicitly document that stream-open is serialized per session (acceptable for demo, state it as a known limit in Thesis.md and drop the 'unlimited/scale' framing from test step 4), or (b) change run_client_driver to pipeline: keep a VecDeque<oneshot::Sender> of pending opens and loop poll_new_outbound until Pending, draining open_rx greedily. Option (b) is a real code change to mux.rs that contradicts the plan's 'UNCHANGED in shape' claim — pick one and write it down. Add a concurrency test (open 50 inbound conns across 2 routes simultaneously, assert all complete).
- **[CRITICAL] Persistence failure mode — durable port allocation leaks on every token-expiry reconnect (open_question #2 is load-bearing and unresolved)**
  - Problem: The plan bakes tcp public_port into the 10-minute token and makes website the allocator via port_pool FOR UPDATE SKIP LOCKED. The agent reserve() loop (service_host.rs lines 54-68) calls reserve() AGAIN whenever connect_and_serve returns Err — and the token TTL is 10 min while sessions can last hours. On every reconnect after expiry the agent POSTs /api/tunnels/request again. If request_tunnel allocates a NEW tunnel row + NEW port each call (the obvious implementation), every reconnect leaks a port_pool row marked tunnel_id=NEW and orphans the old tunnel row, and with pool size 20000..20100 (101 ports) the pool exhausts after ~100 reconnects across all users. The plan flags this in open_questions #2 but does NOT specify the reuse query — and request_tunnel as designed has NO input that ties a re-reservation to an existing tunnel (the agent sends only routes:[{mode,local_port}], not tunnel_id). So the website CANNOT know this is a reconnect vs a new tunnel.
  - Fix: Make request_tunnel idempotent per (owner_id, sorted route signature): SELECT an existing tunnel for this user whose route set (kind+local_port multiset) matches and status IN ('awaiting_agent','offline','online'); if found, REUSE its subdomain + already-allocated port_pool rows and just re-mint the token (this mirrors the existing in-memory 'reuse awaiting_agent' logic at tunnels.rs:58-70). Only allocate fresh subdomain/ports when no match. Add a reconciliation sweep (plan mentions it for crash; also needs to run on a timer) that releases port_pool rows whose tunnel's nf:tunnel:live key is absent for > grace period. Without this the demo's own test step 6 (restart) plus normal multi-hour operation exhausts the pool.
- **[MAJOR] Security — SNI/Host spoofing lets any authenticated user hijack another user's subdomain routing**
  - Problem: route_and_splice resolves state.routes by the subdomain parsed from the attacker-controlled Host header (:80) or SNI (:443) and forwards to whatever agent registered that subdomain. The token authorizes which subdomain an AGENT may REGISTER, but on the inbound public path there is NO check tying the connecting friend to anything — that's correct (friends are anonymous). The real spoofing risk is at REGISTRATION: handle_agent reconciles claims<->bindings by route_id and binds the signed port, but the plan's verify_tunnel_token only checks structural validity (v==1, host.is_some for http/https). It never checks that claims.subdomain matches a subdomain the website actually allocated to claims.sub — the token is self-asserting. Today that's fine because website mints it. But the bigger gap: two agents presenting tokens for the SAME subdomain (e.g. a replayed/leaked 10-min token) will both try to register into state.routes keyed by subdomain; the second insert silently overwrites the first (HashMap::insert), hijacking live traffic, and on the loser's teardown it will remove() the subdomain key the winner now owns, dropping the victim. The plan's teardown 'removes all registry entries' by subdomain with no ownership/generation check.
  - Fix: On register, reject if state.routes already contains the subdomain with a DIFFERENT tunnel_id/owner (return CoreReply::Error 'subdomain already live'). On teardown, only remove the registry entry if its tunnel_id matches this session's tunnel_id (store a generation/session id in RouteHandle and compare before remove). Also: the website should treat the token's subdomain as authoritative-by-mint but the core should additionally confirm via the tunnel_up round-trip OR by checking the Redis nf:route:host key isn't owned by another node before claiming it.
- **[MAJOR] Build/deps — redis ConnectionManager feature is missing and the 'macros'/runtime-query story is internally inconsistent**
  - Problem: website_backend/Cargo.toml has redis = { version = '0.27', features = ['tokio-comp'] } — NOT 'connection-manager'. The plan's db/connection.rs uses redis::aio::ConnectionManager, which in redis 0.27 is gated behind the 'connection-manager' feature. As written the website will NOT compile. Same for core: core_proxy_backend/Cargo.toml currently has NO redis dependency at all (verified: grep returned nothing), yet state.rs/CoreState is to hold redis::aio::ConnectionManager. Separately: website Cargo.toml enables sqlx feature 'macros' AND the plan insists on runtime sqlx::query (NOT query!) 'so cargo build never needs a live DB'. That goal is correct, but 'macros' alone doesn't force compile-time checking (only query!/query_as! do) — so leaving 'macros' on is harmless; however the plan should drop the implication that 'macros' must be removed and must NOT use any query! macro anywhere (one stray query! reintroduces the live-DB build requirement and breaks docker-up-then-build).
  - Fix: Add 'connection-manager' to website's redis features; add redis = { version='0.27', features=['tokio-comp','connection-manager'] } to core_proxy_backend/Cargo.toml (plan says 0.27 — confirmed in Cargo.lock). Audit every DB call site to use sqlx::query/query_as with runtime binding only; add a CI/grep guard `! grep -rn 'query!' website_backend/src` to enforce the no-compile-time-macro rule the friction-free build depends on.
- **[MAJOR] Resource leak on teardown — tcp listener tasks and Redis keys are not all reclaimed; DDoS blacklist grows unbounded**
  - Problem: ActiveTunnel.listener_handles:Vec<JoinHandle> is aborted on teardown (good), but the plan registers tcp routes into state.port_routes keyed by public_port and http/https into state.routes keyed by subdomain — teardown must remove from BOTH maps for all routes of the tunnel, AND release the port_pool rows (owned by website via tunnel_down), AND DEL the Redis nf:route:host / nf:route:port / nf:tunnel:live keys. The plan's handle_agent teardown lists 'removes all registry entries + aborts all listener_handles' but the Redis DEL is in reporter::tunnel_down which is best-effort (debug! on failure, never retried). If the website is down at teardown, the port_pool row is NEVER released (website owns it) and the Redis key only self-expires after 30s — but the Postgres port_pool.tunnel_id stays set forever because nothing re-runs release. Also DdosProtector.blacklist is a Vec that only grows for process lifetime (filter.rs:27) and the plan's Phase 5 adds a no-TTL Redis nf:blacklist set — a single spoofed-source-IP flood (trivial on a relay) permanently blacklists arbitrary victim IPs cluster-wide with no expiry or eviction.
  - Fix: Make port release a Postgres-authoritative reconciliation: a periodic website job `UPDATE port_pool SET tunnel_id=NULL WHERE tunnel_id IN (SELECT id FROM tunnels WHERE status='offline' AND last_seen < now()-interval '60s')` so a missed tunnel_down still frees ports. Teardown in core must iterate the tunnel's route_ids and remove from state.routes (by subdomain) AND state.port_routes (by each public_port) under one lock pass. Give nf:blacklist a TTL (e.g. 1h) and cap the in-process Vec (use a HashSet with timestamps + eviction); never trust source IP for permanent bans behind any relay/proxy that rewrites src.
- **[MAJOR] Local-testability — test_plan step 6 (durability/restart) cannot pass as written because the agent reconnect path re-reserves with a NEW token but the core has no durable port_pool reload**
  - Problem: Step 6 kills both planes, restarts website (reloads tunnels/routes/port_pool from Postgres — OK) and core, and claims 'core reclaims its port_pool rows'. But core does NOT own Postgres (plan decision #7: core has no PgPool). Core only learns which ports to bind from the SIGNED TOKEN at agent handshake. On restart, core's in-memory state.routes/port_routes are EMPTY; it rebinds a port only when the agent reconnects and presents a token containing that port. The agent's reserve() (service_host.rs) on Err re-POSTs /api/tunnels/request and gets a token — but per critical issue #2, unless request_tunnel is idempotent, that token may carry a DIFFERENT port, so the assertion 'SAME tcp port' FAILS. Even if idempotent, there is a race: between core restart and agent reconnect, the bound port is free; if a SECOND user's request_tunnel ran FOR UPDATE SKIP LOCKED it could grab the port that user-1's durable row still claims (because port_pool.tunnel_id is still set to user-1 — so actually SKIP LOCKED won't hand it out; OK). The deeper problem: the test asserts behavior that depends entirely on the unspecified idempotent-reservation query. The test 'proves' durability only if that query exists.
  - Fix: Specify the idempotent reservation query (issue #2 fix) FIRST, then step 6 is sound. Add an explicit intermediate assertion to the test: after restart but BEFORE agent reconnect, `psql -c 'SELECT subdomain, public_port FROM tunnels JOIN routes...'` shows the SAME rows (proves Postgres durability independent of the agent). Then after reconnect assert the SAME port is bound. Without splitting these, a green test could mask a re-allocating reservation.
- **[MINOR] SNI/Host parsing — fragmentation and TLS record-spanning ClientHello will fail-closed and break real clients (esp. step 2 with curl --resolve)**
  - Problem: The hand-rolled SNI parser caps the ClientHello buffer at 8192 and 'buffers until 5+rec_len present'. A ClientHello can span MULTIPLE TLS records, and with large client cert chains / many extensions (some browsers, and rustls with session tickets) can exceed 8192 — the plan's parser then returns NoSni/NotTls and CLOSES. The HTTP path caps at max_header_bytes=16384 and on 'no Host within cap' returns 400. Both are fail-closed, which is safe but the test_plan's optional browser test and even `curl --resolve` over TLS 1.3 with a 2048-bit cert may produce a ClientHello near/over 8KiB once GREASE + ALPN + key_share are present. The replay-in-preamble design also requires replay_len <= u16::MAX (fine) but the peeked bytes must be the EXACT prefix including any bytes already read past the SNI — the encode_preamble replay is &buf (the whole peeked buffer), so the agent replays the full ClientHello; correct, but only if the core peeked the COMPLETE record and didn't consume into the next record. With copy_bidirectional starting after the peek, any bytes the client already sent beyond what was read into buf are still in the socket and will flow normally — OK. Net: the 8192 cap is the real risk.
  - Fix: Raise the ClientHello buffer cap to at least 16384 (TLS record max is 16384 plaintext per record; ClientHello fits in one record but be generous) and explicitly handle the multi-record case by continuing to read until the handshake message length (3-byte) is satisfied, not just the first record length. Add a captured real-browser ClientHello (>8KiB with GREASE/ALPN) to the unit-test table so the cap regression is caught locally.
- **[MINOR] Frontend/API contract drift — stop button and request modal send the wrong identifier; route DELETE param type mismatch**
  - Problem: Verified: frontend/views/dashboard.html:113 calls stopTunnel('${t.subdomain}') and client.js:58 does DELETE /tunnels/{subdomain}; the plan changes the route to DELETE /api/tunnels/{tunnel_id} (Path<i64>). If the frontend is updated to pass tunnel_id but any cached client.js or the admin view still passes subdomain, axum's Path<i64> extractor will 400 on a non-numeric subdomain. Also client.js:57 requestTunnel() sends NO body today; the new contract requires a JSON routes array — an un-updated caller yields an empty/!json body and request_tunnel's Json<RequestTunnelReq> extractor returns 422, which the test_plan's curl (which DOES send a body) won't catch but the real UI will.
  - Fix: Update BOTH client.js methods and EVERY caller (dashboard.html request modal + stop button + admin all_tunnels view) in the same change; keep the DELETE route param as {tunnel_id} and ensure the UI always has tunnel_id from the get_tunnels TunnelView. Consider accepting either i64 or a subdomain string at the route for one release to avoid hard breakage, or bump an API version.
- **[MINOR] Allocation race — subdomain ON CONFLICT retry and port_pool SKIP LOCKED are individually safe but the multi-route reservation is not atomic**
  - Problem: request_tunnel allocates a subdomain (INSERT ON CONFLICT DO NOTHING RETURNING, retry 5x) and THEN allocates N tcp ports (FOR UPDATE SKIP LOCKED) and THEN inserts tunnels+routes and mints the token. If these are not wrapped in ONE transaction, a failure after popping ports but before committing the tunnel row leaks ports (the plan's 'SADD them back' only covers the Redis advisory mirror, not the authoritative Postgres port_pool.tunnel_id which was UPDATEd). The plan even notes 'on any failure after popping ports, SADD them back' — that addresses the Redis cache but the Postgres UPDATE that set port_pool.tunnel_id is the authoritative leak.
  - Fix: Wrap the whole reservation in a single sqlx transaction: BEGIN; insert tunnel (get id); for each tcp route UPDATE port_pool ... RETURNING port (the FOR UPDATE SKIP LOCKED CTE) using the new tunnel_id; insert routes; COMMIT. On any error the transaction rolls back and port_pool.tunnel_id reverts automatically — no manual SADD-back needed for correctness (keep the Redis mirror refresh post-commit).
- **[MINOR] install.sh CAP_NET_BIND_SERVICE — AmbientCapabilities with NoNewPrivileges needs the cap in the bounding set AND the unit currently has no User= (runs as root, making the cap moot or the hardening contradictory)**
  - Problem: Verified install.sh writes NoNewPrivileges=true and has NO User= directive, so the service runs as root today — meaning it can already bind :80/:443 with no capability changes. The plan's addition of AmbientCapabilities=CAP_NET_BIND_SERVICE is only meaningful if a non-root User= is ALSO added; with root it's a no-op, and with NoNewPrivileges=true + a non-root user you must ALSO set CapabilityBoundingSet to retain the cap. The plan mentions CapabilityBoundingSet but not the User= prerequisite, so as written it either does nothing (root) or, if someone adds User= without the full cap trio, the core fails to bind :80.
  - Fix: Decide the prod model: simplest is keep running core as root (drop the AmbientCapabilities change entirely — it's a no-op). If dropping privileges, add User=natforge, AmbientCapabilities=CAP_NET_BIND_SERVICE, CapabilityBoundingSet=CAP_NET_BIND_SERVICE together, and keep NoNewPrivileges=true. Document which. For LOCAL testing none of this matters because HTTP_PORT=8080/HTTPS_PORT=8443 avoid privileged binds — make sure dev defaults in config.rs are 8080/8443 not 80/443 so `cargo run` works without sudo.
